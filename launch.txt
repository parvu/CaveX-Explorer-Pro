# ROOT CAUSE FOUND (real request -- diagnose via GCS_PID_MASK/PID_TUNING,
# per ArduPilot's own real diagnostic method): added GCS_PID_MASK=2 to
# tracked_vehicle_speed_tuning.parm (enables live PID_TUNING/PID_TUNING_
# ACCZ MAVLink telemetry for the throttle-speed loop, straight from
# AR_AttitudeControl::get_throttle_speed_pid_info(), Rover/GCS_MAVLink_
# Rover.cpp) and wrote a pymavlink listener on mavproxy's UDP out port
# 14551 to capture it live during a drive. RESULT: ArduPilot's own
# INTERNAL speed target (PID_TUNING's "target"/desired field) settled at
# ~-0.10 for a commanded +0.4 -- wrong magnitude AND wrong sign -- while
# "actual" tracked "target" almost exactly (e.g. target=-0.1010,
# actual=-0.1040). The PID/FF loop itself is healthy and NOT the problem
# -- the bug is entirely upstream, in whatever computes _desired_speed
# from the incoming GUIDED command.
#
# Traced further: compared ArduPilot's own reported heading (/ap/pose/
# filtered orientation) against real ground truth (gz pose) at the same
# moment -- ArduPilot's own yaw ~96deg vs real ground-truth yaw ~-11deg,
# a ~107deg internal heading error. Rover's GUIDED mode decomposes an
# incoming world-frame velocity into heading+speed internally; with
# ArduPilot believing it's facing ~107deg away from its true heading, the
# speed component it computes for "drive toward this world-frame
# direction" comes out small and NEGATIVE -- exactly matching the
# observed target=-0.10.
#
# This is the SAME root problem as the earlier-documented "ArduPilot
# heading drift" bug (this file's own history above, measured then at
# ~91deg) -- this vehicle still has no GPS/navsat SENSOR wired up, but
# ArduPilot SITL's own simulated GPS (SIM_GPS1_TYPE, driven by the FDM's
# ground-truth position) IS already active by default (confirmed live:
# "EKF3 IMU0/IMU1 is using GPS" in the console log) -- it just was never
# being used for YAW, only position/velocity.
#
# FIXED: added EK3_SRC1_YAW=2 (AP_NavEKF_Source::SourceYaw::GPS,
# tracked_vehicle_speed_tuning.parm) -- the standard, well-supported
# ArduPilot mechanism for a no-compass-but-has-GPS vehicle: EKF3 derives
# yaw from the GPS velocity vector's course-over-ground instead of pure
# gyro dead-reckoning. Live-verified via real ground-truth displacement
# (not ArduPilot's own telemetry, which turned out unreliable here -- see
# below): real speed jumped from ~10-13% of commanded to ~60-65%
# sustained over two separate 10s/30s windows, with good direction early
# on (~5deg off-axis). This is a genuine, large, confirmed improvement --
# the earlier bridge-boundary rotation fix (cmd_vel_to_ardupilot.py/
# track_cmd_vel_bridge.py) stays in place as a real, useful supplement,
# but THIS is what fixes ArduPilot's own internal navigation math.
#
# NOT FULLY CONVERGED / caveats found while verifying: (1) ArduPilot's
# own reported heading (/ap/pose/filtered) was still ~85deg off from

# FURTHER INVESTIGATED (real request: "verify magnetometer calibration
# ... use ground truth as GPS"), DEEPER BUG FOUND, NOT FIXED:
#
# Magnetometer: confirmed ArduPilot SITL simulates a compass
# automatically (AP_Compass_SITL backend, COMPASS_ENABLE=1 by default)
# completely independent of this vehicle's own Gazebo SDF (which has no
# magnetometer sensor at all -- that only ever described the real-
# hardware concept, not this SITL build). Its injected-error model
# (SIM_MAG1_OFS/SCALING/FAIL) is zero/ideal by default -- nothing to
# "calibrate" in the traditional sense. Switched EK3_SRC1_YAW 2->3
# (GPS_COMPASS_FALLBACK) to actually use it, matching ArduPilot's own
# documented preset for this scenario.
#
# GPS as ground truth: SIM_GPS1's own noise/velocity-error params
# (HNSE/NOISE/VERR) were already 0 by default -- the real gap was
# latency/rate (SIM_GPS1_LAG_MS=100, SIM_GPS1_HZ=5 by default). Set
# SIM_GPS1_LAG_MS=0, SIM_GPS1_HZ=50 to make it behave as close to
# instantaneous ground truth as SITL's architecture allows.
#
# RESULT: neither change improved heading convergence. Live-verified
# (fresh eeprom, ruling out the persistence gotcha): ArduPilot's own
# reported yaw was STUCK at ~97.2deg, essentially IDENTICAL across
# repeated samples taken 3s apart over a 12s window (varying only in the
# 4th decimal place) -- too stable to be raw gyro-only dead-reckoning
# drift, but wrong by a consistent ~98-100deg from real ground truth the
# whole time, regardless of GPS-only vs GPS+compass-fallback yaw source.
#
# REAL HYPOTHESIS (not yet verified): this pattern -- a highly stable,
# confidently-held, but consistently WRONG heading, unaffected by which
# aiding source is used -- fits a fixed coordinate-transform bug
# upstream of the EKF, not a fusion/convergence problem. Both GPS-course

# transform (model.sdf.tracked) -- if that transform's yaw component is
# wrong for this vehicle's real mounting convention, EVERY internal
# ArduPilot attitude source would be consistently, self-reinforcingly
